# XTM-Miner test report

Updated 2026-10-20. This is a milestone report, not a claim that mining, accepted pool work, or standalone APK integration has been validated.

## Passed in the Sandbox

**Pinned-source host build.** The bundled archive checksum is `2cb21d5a0b32c6c504f4b5481f1bd465626759791188f343d854fc6439ca9ce1`; its source pin is XMRig v6.26.0 at `b2ca72480c58d197e18c885d9fc1a0c8d517e60a`. The patched engine previously compiled as x86_64 Linux with TLS enabled. Environment recorded from that build: GCC 13.3.0, CMake 3.28.3, Ninja 1.11.1, OpenSSL 3.0.13, and libuv 1.48.0. GPU backends, hwloc, MSR tuning, benchmark, HTTP, and DMI were disabled. The engine reported XMRig 6.26.0.

**CMake prefix check.** A fresh host-only CMake configure using `-DXMRIG_DEPS=/usr -DCMAKE_PREFIX_PATH=/usr` succeeded and found OpenSSL and libuv under `/usr`. This confirms the prefix settings in the Linux host layout; it does not validate Termux's `$PREFIX` layout.

**TLS behavior.** Synthetic local TLS checks against the patched host binary accepted a CA-signed certificate with matching `localhost` hostname and rejected a wrong hostname and an untrusted certificate. XMRig exited after SIGINT within the test timeout. These were local test servers, not the Tari pool; no pool work was hashed.

**Launcher behavior.** Host mock tests passed explicit-start gating, input validation, `rx/0` and wallet/worker config, TLS-default configuration, fail-closed handling when the CA bundle is unreadable, private mode-600 config cleanup, duplicate-session refusal from a second source copy sharing the same simulated Termux prefix, SIGINT/TERM forwarding, child reaping, persistent lock cleanup, and no orphan mock process. These tests used a mock engine, not Android process behavior or actual mining.

**Source and shell checks.** Bash syntax checks passed individually for the build, launch, test, and launcher-test scripts. The archive SHA-256 check passed. The TLS patch applied to a clean extraction of the exact pinned archive and its verification marker was present. The build and test scripts refused to proceed in the Sandbox with a non-Termux `PREFIX`.

## User-provided physical phone evidence

The user reported a Google Pixel 9a running Android 17/API 37, ABI `arm64-v8a`, and Termux Google Play `2026.10.09` (`termux-tools` 3.0.9). The reported `PREFIX` was `/data/data/com.termux/files/usr`; both `uname -m` and `dpkg --print-architecture` reported `aarch64`. These are user-provided phone outputs, not direct device-tool observations by this Sandbox.

The user verified the ARM64 test ZIP's SHA-256 in shared storage and again after copying it into Termux's private home, then extracted it there. They installed the requested Termux packages. Their reported build used Clang 21.1.8, CMake 4.3.4, Ninja 1.13.2, OpenSSL 3.6.3, and libuv 1.52.1. CMake found both libuv and OpenSSL under `$PREFIX`; the source archive checksum passed, the TLS patch applied, and all 162 build tasks completed. The build script's `--version` check reported XMRig 6.26.0, built with Clang 21.1.8 and 64-bit AES, at `bin/xtm-miner`. Warnings included an unsupported optimization flag and upstream deprecated/unused-field warnings; no compile or link failure was reported. This establishes successful on-device ARM64 Termux compilation and version-command execution, not mining.

The first Termux smoke-test attempt stopped at its command preflight with `Missing openssl`. The user's output showed no `$PREFIX/bin/openssl` executable but did show `libssl.so` and `libcrypto.so` symlinks under `$PREFIX/lib`. Termux's current OpenSSL recipe defines `openssl-tool` as a subpackage that includes the `bin` directory [4]. The regular smoke test does not use the CLI, so `scripts/test-termux.sh` was corrected to require `openssl` only when `--tls-local` is selected. The user verified and installed the corrected script, then passed the ordinary ARM64 smoke suite: source checksum, dependencies, binary version/help, and mock launcher checks. After installing `openssl-tool`, the user also passed the optional on-device local TLS regression: a CA-signed matching hostname was accepted and both wrong-host and untrusted certificates were rejected. This validates the patched native binary against temporary local test servers on the phone; it is not a production-pool test.

The user also verified and ran `scripts/test-native-launcher.sh` on the phone. It started the real compiled XMRig through the launcher (reported wrapper PID `25850`, native child PID `25866`), refused a second launcher instance, then sent TERM. The script reported that the real native child stopped and the Termux-wide lock was released. It used `TARI_TEST_ADDRESS` and unreachable `127.0.0.1:1` only; no public Tari address, production pool, or mining job was used. This establishes actual native-launcher start, duplicate prevention, TERM stop, child reaping, and lock cleanup on that phone. It does not establish hashing, interactive Ctrl-C handling, or pool connectivity.

## Not established

No production-pool connection was made. No public receiving address or pool credentials were used. Actual Tari RandomX job hashing, accepted shares, pool-side worker evidence, payouts, and live TLS compatibility remain unverified. A successful build, version check, or pool login alone is not accepted-share evidence.

No physical readings were reported for process RSS, Android memory limits, CPU or battery temperature, battery drain, screen-off behavior, lifecycle, cooldown, or interactive Ctrl-C reliability. The real launcher did pass one bounded TERM stop and child/lock cleanup test on the phone. Manual foreground Ctrl-C remains the next no-pool gate. No Android cross-build, emulator test, standalone APK/JNI build or install, dashboard, signing, or APK lifecycle test has run. Do not claim device safety, background continuity, or universal compatibility.

The first manual foreground Ctrl-C attempt reached the expected loopback `connection refused` message, then the user reported that Termux exited and restarted instead of returning to the shell. The result is **not passed**. The follow-up diagnostic found no `xtm-miner` or `xmrig` process and no XTM-Miner lock, so the restart left no observed orphan. At that snapshot `/proc/meminfo` reported `MemAvailable: 1162448 kB`, `MemFree: 226788 kB`, and `SwapFree: 99404 kB`; this clears the wrapper's 512 MiB light-mode preflight, but is not an Android per-process limit or thermal-safety measurement. The available filtered log showed old `cpuminer` linker errors from a different `termux-miner_v2.7` directory dated 2026-10-19, but no current XTM-Miner fatal signal, Android low-memory event, or Termux crash record. It also showed Termux binder warnings, which are insufficient to attribute the restart to the launcher. The installed Google Play Termux build is an experimental, separately maintained distribution with known missing functionality and bugs relative to stable sources [5]; this is an environment consideration, not a diagnosed cause.

The follow-up no-miner `test-interactive-signal.sh` probe also restarted the Termux session. Its persistent private log recorded both `event=READY` and `event=INT` for the foreground probe process before the restart. Therefore, SIGINT reached the script even though the terminal session did not recover normally. This rules out XMRig, a wallet, and network activity as necessary conditions for the observed reset, but does not identify the Google Play Termux issue's root cause. Interactive Ctrl-C is not used as a pass criterion for this phone/build. The user reported that Termux Python exposes neither high-level `os.pidfd_open` nor `signal.pidfd_send_signal`. A separate `scripts/stop-termux.sh` helper therefore calls Linux pidfd syscalls directly through standard Python `ctypes`, verifies the current process executable through the opened pidfd's PID, then sends TERM and waits through that same process handle. Host tests verified the direct syscall path; physical Android validation remains the next no-pool stop-control test.

During that physical helper validation, `pidfd_open` and pidfd-bound TERM/poll passed for a temporary Python child. The live loopback XMRig helper then failed closed because `/proc/27340/exe` represented Android `linker64`, not the project path. The user-provided `/proc/27340/maps` did show executable mappings of the exact current `bin/xtm-miner` path with matching device/inode. This is consistent with Google Play Termux's `system_linker_exec` approach [5]. The helper now accepts that path only after opening the pidfd and confirming an exact executable map—same real path, device, inode, and execute permission—or the same exact path representation. It then sends pidfd signal 0 before TERM, so a target that exited during procfs inspection fails closed rather than validating a reused numeric PID. Host tests cover direct launch, both Android-style mapping representations, pidfd liveness, and refusal of an unrelated executable. The updated fallback still requires physical no-pool validation.

The final updated helper passed its physical no-pool validation. From a second Termux session it reported `Requesting TERM stop for XTM-Miner PID 27340 through pidfd`, `Native child PID 27340 exited after TERM`, and `PASS: native child stopped and launcher released the lock.` The first session displayed XMRig's `SIGTERM received, exiting` and returned to its normal shell prompt; the second session confirmed `Lock released.` This establishes externally initiated, pidfd-bound TERM Stop, native exit, lock cleanup, and first-session shell recovery on this phone/build. The user did not include the output of the accompanying `ps` process-list command, so the final independent no-orphan process-list observation remains pending.

## Diagnosed command/test issues

- The first Termux smoke test required the `openssl` CLI even when only the ordinary smoke suite was requested. Termux separates that CLI into the `openssl-tool` subpackage [4]. The script now gates that prerequisite on `--tls-local`; the user verified the correction by passing both ordinary and optional local TLS suites on the phone.
- The manual foreground Ctrl-C test caused the Termux session to restart. The expected loopback refusal appeared first. Available logs were inconclusive and included unrelated older `cpuminer` linker errors. A post-restart diagnostic found no miner-like process and no XTM-Miner lock, so no orphan was observed.
- The no-miner signal probe also restarted Termux but persistently recorded `READY` and `INT`, proving SIGINT delivery to the foreground script. It did not identify the application/session reset cause. Interactive Ctrl-C is excluded from subsequent physical test controls on this Google Play Termux build; a PID-identity-validated external TERM helper is prepared instead.
- A clean-source patch-check command initially checked the TLS marker after a dry-run only, so it exited before applying the patch. The corrected check applied the patch, then verified the marker; it passed.
- Earlier host configuration lacked libuv development headers; installing the host `libuv1-dev` package resolved that build prerequisite.
- The first compile found the TLS patch needed `<openssl/err.h>`; adding the include fixed the build.
- The launcher mock fixture originally placed its binary outside the wrapper's expected project root; the fixture was corrected.
- The TLS test listener initially bound only one address family while `localhost` resolved to IPv4 or IPv6. A dual-stack loopback listener fixed the test.
